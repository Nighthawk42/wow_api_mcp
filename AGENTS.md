# AGENTS.md

Guidance for AI agents working in this repository.

## What this is

A TypeScript MCP server (stdio transport) exposing the WoW addon API across every `Gethe/wow-ui-source` track. Data comes from four places:

1. **Parsed Blizzard docs** — `data/<flavor>.json.gz`, generated by `npm run ingest` from `Blizzard_APIDocumentationGenerated` Lua files in [Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source). Never hand-edit anything in `data/`.
2. **Warcraft Wiki** — fetched live via the MediaWiki API, cached on disk (~24h).
3. **UI source code** — shallow clones per flavor in the OS cache dir, searched with `git grep`.
4. **The local game install** — `.build.info`, `.flavor.info`, client executable version resources, and addon `.toc` files, used to decide which flavor a question is about.

## Commands

```bash
npm run build        # tsc → dist/
npm run dev          # run server from source (tsx)
npm test             # vitest (offline)
npm run typecheck    # tsc --noEmit
npm run verify-data  # assert data/ manifest, name index and payloads agree
npm run ingest       # regenerate data/ (discovers upstream branches itself)
npm run smoke        # end-to-end: calls every tool via in-memory client
```

## Layout

- `src/index.ts` — server entry (McpServer + StdioServerTransport)
- `src/server.ts` — tool registration and the client-facing `instructions` string
- `src/flavors.ts` — curated per-track metadata (label, channel, product codes, install dirs)
- `src/data/paths.ts` — data directory resolution, gzip read/write
- `src/data/manifest.ts` — `_manifest.json` + `_names.json.gz`, the cheap always-loaded tier
- `src/data/loader.ts` — lazy per-flavor payload load, MiniSearch index, LRU
- `src/install/` — install discovery (`detect.ts`), `.build.info`/`.flavor.info` (`build-info.ts`), PE version resources (`pe-version.ts`), `.toc` parsing (`toc.ts`), build → flavor scoring (`resolve.ts`)
- `src/tools/` — one file per tool group: `api.ts`, `install.ts`, `wiki.ts`, `source.ts`; shared schemas in `common.ts`
- `src/lua/parse-docs.ts` — luaparse AST → JSON (never executes Lua)
- `src/wiki/client.ts` — MediaWiki client + turndown + disk cache
- `src/source/repo-cache.ts` — shallow-clone manager + git grep
- `scripts/ingest.ts`, `scripts/verify-data.ts`, `scripts/smoke.ts`
- `tests/` — vitest; parser fixtures live in `tests/fixtures/`

## Conventions

- ESM (`type: module`), Node 20.11+ (`import.meta.dirname`), strict TypeScript.
- Tool inputs validated with zod; tool names are `snake_case`.
- All tool responses are plain text/markdown (broadest client support).
- Every tool declares `annotations` (`READ_ONLY`, or `READ_ONLY_NETWORK` for wiki/source tools, from `src/tools/common.ts`) and wraps its handler in `guard`, so failures come back as `isError: true` text rather than protocol errors.
- Flavor IDs are exactly the upstream branch names — never invent aliases.
- Keep stdout clean in server code: stdio transport owns it; log to stderr.

## Things that will bite you

- **The flavor list is data-driven.** `availableFlavors()` reads `data/`; there is no hardcoded union type. Adding a track means running the ingest, not editing an enum. `src/flavors.ts` only supplies labels and detection hints, and unknown branches fall back to sensible defaults.
- **Ingest output must stay deterministic.** `generatedAt` is the upstream commit date, not wall clock, and gzip is written with fixed settings. Re-running an unchanged track must produce byte-identical files, otherwise the daily refresh commits noise forever.
- **Don't load every flavor to answer one question.** There are a dozen payloads at several MB parsed each. Availability checks go through `_names.json.gz` (`hasName`), and `list_flavors` reads `_manifest.json`. Only reach for `loadFlavor` when you need actual entry bodies; `WOW_API_MCP_CACHE_FLAVORS` bounds how many stay resident.
- **Build number beats product code** when resolving an install to a track. They do not line up one-to-one — see the comment in `src/install/resolve.ts`. `tests/install.test.ts` pins the two real cases that would otherwise regress.
- **Blizzard packs exe versions oddly.** Builds above 65535 do not fit the 16-bit version-resource fields, so `12.1.0.69814` is stored as `1201.0.6981.4`. `decodeExeVersion` unpacks it; smaller builds use the plain encoding.
- **The refresh workflow pushes to `main` directly.** No PR to merge. If you change the data format, bump `DATA_FORMAT_VERSION` and make sure `verify-data` covers the new invariant, because that job is the guard on every PR.
- **Generated data must be identical on every platform, and bytes are not the test.** gzip output differs between zlib builds, so `writeJson` compares decompressed content and skips unchanged files; `parseDocumentationFile` normalizes line endings because a Blizzard doc string contains an escaped literal newline that CRLF checkouts would capture differently. Both are load-bearing for the daily refresh — break either and the job commits megabytes of churn every day. `tests/data-paths.test.ts` and the line-ending block in `tests/parse-docs.test.ts` pin them.
- **`npm run typecheck` is not `npm run build`.** The build config scopes `rootDir` to `src/`; `tsconfig.check.json` is the one that also covers `scripts/` and `tests/`. Use the former for shipping, the latter for checking.
- **Never block the event loop.** The stdio transport shares the thread with tool handlers, so a synchronous call freezes every in-flight request and the client's pings. `SourceRepoCache` runs git through async `execFile` (the first fetch per flavor takes about a minute) and dedupes concurrent preparations per flavor; keep new I/O async too.
- **Publishing goes through `release.yml`,** whether triggered by hand or called by the refresh job. Don't add a second publish path.
